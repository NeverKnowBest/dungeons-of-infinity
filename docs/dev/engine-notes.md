# Engine notes

Working notes on how the Dungeons of Infinity engine is put together, kept so that new work (and new sessions) can start fast.

## Levels and rooms

* A level is a grid of rooms. Layouts live in `game/datafiles/data/data_d` (dungeon templates, by class; the Special class holds fixed layouts such as the save tent and the Sanctuary hub at index 5).
* Each room uses a room template from `game/datafiles/data/rooms/` (one file per class), converted from the Tiled maps in `data/room-templates/`. Class Other = 9, subclass Unique = 2 holds hand made rooms like `Sanctuary`.
* Rooms are made of 256px quadrants: a 2x2 room is 512x512. Template object coordinates are relative to the room's top left corner.
* Collision is only `oWall` instances, created with `WallObj_Create(layer, x, y, tilesW, tilesH)` (8px tiles).
* Instance layers by depth: `ObjsHigher_Upper` 400, `Objs_Upper` 600, `ObjsDoors_Upper` 700, `ObjsFloor_Upper` 800, tile floors 1400. Anything drawn with `PixelRender_Normal()` needs a `FloorLevel` variable.
* `data_d` is stored with Git LFS. The room template files are plain git (see `.gitattributes`), so their diffs show which templates changed.

## Room templates (`game/datafiles/data/rooms`)

* `tools/templates/convert.py` builds the room template files from the Tiled maps (one per class: `Room Templates <Class>.json`). It is a port of the old GameMaker project `editors/room-template-parser` (deleted in F5, oct/2026; it is in the git history), and its output was checked equal, by content, to the last `data_r` that project wrote. `game/scripts/__RoomTemplates` and `__Transformations` hold the same enums and transform tables on the game side.
* Until F5 everything was one 46 MB file in Git LFS, `data_r`. Now it is `game/datafiles/data/rooms/<Class>.json`, one file per class, with one template per line. Main_Upper alone is 37.6 MB; GitHub warns at 50 MB, so split it by subclass if it gets close (the validator warns at 45 MB). Each file is an included file in `Zelda.yyp` (`datafiles/data/rooms`).
* `RoomTemplates_Load` reads the ten files in class order into `global.Templates_Room[class][subclass][template]` and prints `Room templates loaded: [[42.0,231.0],...]` (the template counts) to the run output. Class order: Main_Upper, Main_Lower, Stairs, Jails, Village, Mines, Obstacles, Sections, Special, Other. The subclass is the room size (1x1, 1x2, 2x1) for the size based classes, or the Tiled room `type` (Obstacles: Blocks, MovingFloors, SpikeBlocks; Special: Fairy, Shop, GemPond, Treasure, TreasureLarge, Rupee, Gem, Kinstone; Other: Boss, Start, Unique, Save; Village: Main, House, Maze, Exit; Mines: Main, House).
* A Tiled map has a `Rooms` layer (one rectangle per template, with `type` and properties such as `Symetry` and `Split_MainSectionIDs`), one object layer per object type of the class, and for some classes a `Sections` group (Main_Upper has 5 sub groups: Main, 1-3-6-8, 2-4-5-7, 9-...-16, 17-20; the others only Main). Every object has a `Room` property pointing to its room rectangle. The lists of layers per class are in `convert.py` (`OBJ_TYPES`, `SECTION_OBJ_TYPES`) and in `RoomTemplates_Load`.
* `Dungeon_CreateStruct_Room` picks the class from the room's doors and section (Main_Upper, Main_Lower, Stairs, Obstacles, Sections) and the subclass from its size, and `RoomTemplates_Pick` takes the next one of a shuffled list per class and subclass (`RoomTemplates_PickFrom`). Special, Village, Mines and Other are picked by name or type before that and never use a room set.
* What a template must hold: after the pick, `Dungeon_Draw_SpecialObjs` places the room's special object (key, crystal, warp, treasure) on the template's spots (Treasures, Crystals, Pots, PotTreasures, Monuments, Altars; inside the SectionArea when the object is in the section). When it cannot, the room is cleared and picked again from the same shuffled list, forever: a template that fits the doors but has no spots would hang the build. Room set templates are cut off after `ROOMSET_MAXMISSES` (4) such misses per room, then the room takes a shared template.
* `oEnemy_Zol` reads `global.Templates_Room[class][subclass][Room.TemplateIndex]`, but `TemplateIndex` is never set (always 0): it reads the enemy areas of the first template of the class, not of its room. Old behaviour, left as is (changing it changes the reference levels).

* Object positions become relative to the room; a rotated Tiled object (90, -90, 180) is turned into a plain box first (`RoomTemplates_FixObjRotation`).
* Main_Upper and Main_Lower templates are half rooms (256x128 or 256x256). The converter joins every pair whose `SplitConnections` match: the second half is flipped vertically (and also flipped both ways when both halves have `Symetry` 0) and placed under the first. Then touching side walls are joined, duplicated doors removed and carpet door lists merged. That is why 46 Main_Upper halves become 273 rooms. Template 11115 joined with itself unflipped is skipped on purpose (bad zones).
* `DoorCode`: one number per transform (None, FlipH, FlipV, FlipHV, RotateCW, RotateCCW, FlipHRotateCW, FlipHRotateCCW); bit n-1 is set when there is a door at position n (1..24, the coordinates are in `DOOR_XY` / `Data_InitDoorCoordinates`) after that transform. `ZoneCodes[transform][section][zone]` is the same per zone. Doors get `Position` and `Location`. Village, Mines and Other get no codes and allow no transform.
* Numbers are written as floats (`16.0`), like GameMaker writes its reals. The old `data_r` ended with a zero byte (GameMaker `buffer_string`); the new files do not, and `buffer_read(..., buffer_string)` still reads them whole (tested in game).
* Carpet `DoorsFrom` and `DoorsTo` are strings in Tiled. The GML transform split them with `CSVToList` (strings) and still worked in game, so the converter treats them as numbers (the comparison with the real `data_r` showed no difference).
* The old parser ended with `RoomTemplates_GenerateImageSheet` (a debug PNG that read a `RoomMapSpr` nobody set); the converter does not port it.

## Room sets (roadmap F11)

* A level can have rooms of its own: `RoomSet` in the level sheet names a set, and every room of the generic pick tries the set's templates first (same shuffled list, door, section and zone checks, transforms). When none fits, the room takes a shared template (`RoomSetFallback`, true by default; false makes the build fail like a missing template). A level without `RoomSet` picks exactly as before (no random number more), so the 14 reference levels come out the same.
* Files: `data/room-templates/sets/<Set>/Room Templates <Class>.json` (Tiled maps of the classes the set has, same layers as the shared maps) become `game/datafiles/data/rooms/sets/<Set>/<Class>.json`, each template with `"RoomSet": "<Set>"` (and, for joined halves, the name `<top>+<bottom>`, `~` when flipped both ways), plus `rooms/sets.json` (`{"<Set>": ["<Class>", ...]}`). `convert.py` writes them and registers each file as an included file in `Zelda.yyp`; the game only copies included files that are listed there.
* Game side: `RoomSets_Load` (end of `RoomTemplates_Load`) fills `global.RoomSets[$ set] = {Templates, Count, Unused}`, indexed `[class][subclass]` like the shared arrays, and prints `Room sets loaded: {"Example/Main_Lower":[1,0],"Example/Main_Upper":[3,1]}`. `RoomSet_For` gives the set when it has templates for that class and subclass. The set's shuffled lists are its own, so picking from a set never moves the shared lists, and they are made on first use (`RoomSet_For`): a `ds_list_create` at load time shifts every later ds number, and the reference dumps of every level would differ.
* `tools/templates/make_rooms.py` writes the set maps from `rooms.json` (format in `tools/README.md`). How a Main half is built, checked by `make_rooms.py --selftest` (and the validator) against ten shared templates (Main_Upper 663, 11139, 11113, 32618; Main_Lower 11102, 40406, 33044, 40419, 42882, 40295), whose walls, doors, OutOfBounds, LowerFloor and SplitConnections it reproduces exactly:
  * The outline is the box from (16,16) (Main_Lower: (40,40)) to the cut line at the half's bottom, minus the `cut` boxes. Walls are 24 px thick inside the outline: a corner piece at every vertex (convex: `WallCornerXX` in the corner; concave: `WallInnerXX` named after the missing quadrant, placed in the opposite one) and side pieces between them (a concave end extends the side band by the inner corner, a convex end stops before the corner). Walls never close the cut line; the side walls run down to it.
  * Main_Lower: the outline is the lower floor (`LowerFloor`, its lower walls `WallLower*` inside it). The upper walls are not a fixed ring: they are traced the same way around the outline grown by 24 px on every side (clipped to the box from (16,16)), so they sit right against the lower walls, and OutOfBounds covers the rest. A first version kept the upper ring rectangular, which is right only without cuts.
  * Doors sit on straight side pieces at the door coordinates of the joined room (`DOOR_XY`): top 11, 12, 1 and sides 10, 9 / 2, 3 (Main_Lower: 23, 24, 13 and 22, 21 / 14, 15); the side doors at the cut line belong to both halves. SplitConnections are 24x32 boxes at the side walls on the cut line (`y = h - 16`); two halves join when theirs match.
  * Sections (Main_Upper only): group 1-3-6-8 hosts section 1 (top left corner), 2-4-5-7 section 2 (top middle), 9-16 section 9 (wide left), 17-20 section 17 (top strip); `Split_MainSectionIDs` lists them in group order. The mirrored sections (3, 10...) come from the game's transforms. Each group holds everything the room has while that section is active (area, rails with their `SB` shape code, enemies, spots), not only the section.
  * Zones are only needed when water (or anything) splits the floor; a room without zones accepts any doors. The helper refuses a split floor without zones.
* The validator compares the set's game files and generated maps byte for byte with what the tools write (LF), so `.gitattributes` keeps them `eol=lf` on checkout; a new folder of compared files needs the same rule.
* Template objects are candidates, not placements: `Dungeon_Draw_SpecialObjs` draws a random subset of each layer (torches: 1 to 4 picks, `SpawnTorches`; monuments: between `GridW*GridH` and all, at least 128 px apart center to center, `SpawnMonuments`; water: each block with a chance per room when the level's water is random, `Dungeon_Draw_Water`; spikes: each strip with `Chance_SpikeSection`; carpets only in Castle, Water Temple and Aghanim 1 themes, and a full carpet grows from its box to the walls). So a template looks designed when its candidates sit in patterns that any subset still shows: corners, rows on the walls, the axis, symmetric lattices.
* The game keeps most layers off the doors in use by itself: `SpawnObj` (torches, pots, treasures, crystals) skips a spot within 16 px of an `oDoor`, monuments, spikes and altars within 24, kinstones within 32. Water, guru bars and moving spike blocks are not checked. That is why the shared templates put monuments on a door slot's lane (77 of 86 in Main_Upper) and why the composition check (F11b) only keeps the unchecked layers off the lanes.
* Composition (roadmap F11b): `tools/templates/motifs.py` measures how the shared Main halves place each layer (anchor: `corner`, `top`, `top_center`, `side`, `axis`, `field`, `area`; insets [side, top] from the walls, sizes, steps, lattice phase against the middle axis, properties) and writes `data/room-templates/motifs.json`. The insets are free floor between the piece and the nearest non-floor cell (8 px cells, 64 = far); the cut line is not a wall. Measured rules: Torches, Monuments, Pots, PotTreasures, Treasures, Crystals, Kinstones and Altars are mirrored (at least 75% of the pieces whose mirror spot is floor have it, halves with `Symetry` 0 left out); Torches, Monuments and MovingSpikeBlocks never touch each other; water and spikes are mirrored only 63% and 73%, so the check does not ask it (the composer still places everything in pairs). The catalog explains 96% of the Main_Upper pieces and 92% of the Main_Lower ones; the rest are one-off placements. Water never crosses the cut line, while treasure spots, guru bars and lower floor kinstones and pots do.
* `make_rooms.py` composes in this order: the main group's furniture (Torches, Monuments, Altars, Kinstones, Pots, PotTreasures), then the top level water and spikes (avoiding that furniture and every hosted section's rails) and the full carpet, then the main group's spots and areas, then each section group. Composing water first pushed the gallery statues away; composing the spots before water put treasure spots in the pool.
* Claude's shell tool turns `\\` into `\` in the command text, even inside a quoted heredoc: a Python edit script written that way that holds `r'\\b...'` writes a backspace, and the regex silently stops matching (it happened twice in F11). Edit files with the Edit tool, or write the script to a file first; the validator now flags control characters.
* GML: the project has `option_copy_on_write_enabled` false, so arrays passed to a function are the same arrays (writing `_Unused[_Class][_SubClass]` inside `RoomTemplate_GetNextIndex` changes the caller's).

## Project files

* Only resources listed in `game/Zelda.yyp` are compiled. The 424 folders that were on disk but not in it (old scripts such as `_Enemies`, `Init` and `Dungeon_Init`, unused sprites and objects) were deleted in the F1 cleanup (oct/2026); the original 1.2.1 code is on archive.org if one is ever needed. The validator warns about any new orphan folder (`--orphans` lists them).
* When a resource is removed from the project in the IDE, GameMaker leaves its folder on disk. Delete the folder too, or the validator flags it as an orphan.
* An object's `.gml` files only run if the event is in the object's `eventList` in its `.yy`. The leftover event files of the original were deleted in F1; the validator warns about new ones.
* Resource folder names must match the `.yyp` letter case exactly (`objects/oCape`, not `objects/ocape`); Windows does not care, Linux tools do. The 48 mismatches were fixed in F1 and the validator warns about new ones. On Windows a case only rename is not seen by Git with `core.ignorecase=true` (the default); use `git mv old tmp` then `git mv tmp New`.
* `data_d`, the audio and the manuals and references in `docs/` (PDF, DOCX, MHTML) are Git LFS files. Both PCs (home and work) have Git LFS, so the real files are there. A clone without LFS (Claude's cloud sandbox, for example) only has pointers; the validator skips them.
* The only command line parameter the game reads is `-test <file>` (test mode, below; the environment variable `DOI_TEST` does the same). The original had `-t` and `-d` handling in `InitScreen` inside an old `Init` script that was not in the project (deleted in F1; see the 1.2.1 source on archive.org).
* GML evaluates the right side of an assignment before the index on the left: `a[i] = f(i++)` stores at the incremented `i` (the level sheet came out shifted by one). Use `a[i] = f(i); i++;` or explicit indices.
* When Claude writes a file through a shell heredoc on these PCs, a double backslash arrives as a single one and accented text can arrive in the wrong code page: GML strings with an escaped `\n` became real line breaks and `\r`/`\t` in Windows paths became control characters in `tools/README.md`. Write such files with the editor tools, or build backslashes with `chr(92)` and run Python with `PYTHONUTF8=1`.
* Level specific rules live in the level sheet (`scripts/__Levels`, below). Code should read `LevelDef.<field>`, never compare `global.Level.Index` with a `DungeonLevel` member.

## Building and running from the command line

`tools/test/run.py` does all of this by itself (finds the runtime and the user folder, builds in `%TEMP%\doi-test`, runs a test scenario); see "Automated tests" below. Igor is the build tool the IDE runs:

```
<runtime>\bin\igor\windows\x64\Igor.exe -j=8 --project="<repo>\game\Zelda.yyp" --user="%APPDATA%\GameMakerStudio2-LTS2026\<user folder>" --runtimePath="<runtime>" --runtime=VM --prefabs="C:\ProgramData\GameMakerStudio2-LTS2026\Prefabs" --cache="<temp>\cache" --temp="<temp>\temp" -- Windows Run
```

* `<runtime>` is `C:\ProgramData\GameMakerStudio2-LTS2026\Cache\runtimes\runtime-2026.0.0.23` (the active one is named in `C:\ProgramData\GameMakerStudio2-LTS2026\runtime.json`). The user folder is the one inside `%APPDATA%\GameMakerStudio2-LTS2026` (`unknownUser_unknownUserID` when nobody is signed in to the IDE).
* `--prefabs` is required: the project uses the `gm_filter_heathaze` and `gm_filter_pixelate` prefabs, and without it the asset compiler stops with "Prefab libraries that cannot be located".
* `Run` compiles (about a minute) and starts the game; the command only returns when the game closes, so run it in the background. It writes the build to `output/` inside the current folder, so start it from a temporary folder, not from the repository. Everything the game prints (`show_debug_message`, runtime warnings, compile errors) goes to the command output.
* `PackageZip` (making an executable) fails with "Permission Error: Unable to obtain permission to execute" when nobody is signed in to the IDE; `Run` works anyway.
* Screenshots and key presses during a test: PowerShell with `user32` (`SetForegroundWindow`, `GetWindowRect`, `keybd_event`) and `System.Drawing` (`CopyFromScreen`) on the `Runner` process window, holding each key about 0.15 s. Close the game with `Stop-Process -Name Runner`.
* Known noise in the output, not errors of ours: `oCredits_Step_0 ... Index did not map to an existing sound instance` and `Intro_ShowLink ... existing audio asset`.
* After a `Run` build the game data is `%TEMP%\doi-test\output\Zelda\Zelda.win`; `<runtime>\windows\x64\Runner.exe -game <that file>` starts it again without compiling (8 s; `run.py --no-build`).
* `Windows Compile` instead of `Windows Run` builds the same `Zelda.win` without starting the game (`run.py` does this since F3b and starts `Runner.exe` itself). An unknown command makes Igor list the ones it has: `Compile`, `Run`, `PackageZip`, `PackageNsis`, `Clean`, `Package`...
* Why a test window used to flash and take the focus: the project has `option_windows_start_fullscreen` on, so the runtime opens the game in fullscreen and `oInit` (Draw_77) goes windowed a few frames later. The fullscreen switch takes the foreground. The option is bit 0 of the info flags in the `GEN8` chunk of the `.win` (the chunk is the first one, at byte 8; its data starts at 16 and the flags are at 16 + 68, right after the default window width and height, 1600x900 here). `run.py` clears it in a copy (`Zelda_test.win`, next to the real one so the audio groups and data files are found).
* Even windowed, hidden (STARTUPINFO `SW_HIDE`/`SW_SHOWNOACTIVATE`), off the screen and with `WS_EX_NOACTIVATE`, the runner still takes the foreground for about 2 s while it loads (a process started from the app in use has the right to), and `SetForegroundWindow` back to the previous window does not win. What works is a desktop of its own: `CreateDesktopW` + `CreateProcessW` with `STARTUPINFO.lpDesktop` (Python's `subprocess` has no field for it, so `run.py` calls it through `ctypes`). On that desktop the game renders and saves its PNGs normally (same bytes), the foreground of the user's desktop never changes, and the desktop goes away when its handle is closed and the game has ended.
* On the hidden desktop the runtime makes one surface more at start: every `ref surface N` in the dumps is one higher than on the screen (logs and PNGs are the same). `baseline.py compare --handles` ignores it.

## Automated tests (`scripts/__Test`, roadmap F3)

* Test mode starts in `oInit`: `Test_Init` (Create) looks for `-test <file>` or `DOI_TEST`, reads the scenario from the save folder and creates `oTest` (persistent, at -10000,-10000 so room deactivation never reaches it). `Test_Begin` (instead of `room_goto_next` to the title) makes a throwaway user, turns on the scenario's cheats and goes to `Room_Dungeon`, where `oGame` calls `Test_StartLevel` instead of building the intro.
* Nothing is written to disk in test mode: `User_Save`, `Settings_SaveIni` and the arcade high scores return early, and `Error()` logs a FAIL instead of opening a message box (a message box would hang the test). Unhandled GML errors go to `Test_OnCrash` (`exception_unhandled_handler`), which logs the message and the stack.
* Input: steps call `input_verb_set` every frame. Two traps of the Input library (7.0.1): a player with no source (nobody pressed a key yet) does not update its verbs at all, so test mode sets the player to ghost (`input_player_ghost_set(true)`, which also ignores the real keyboard); and forced verbs are dropped while the window has no focus, so `INPUT_ALLOW_OUT_OF_FOCUS` is true in test mode only. `global.AltTabPause` is turned off too.
* `oTest` runs the steps in its End Step, like `oLink` builds the next level there: room activation and level building must happen after the Step events.
* Building a new level over another one: `Dungeon_Clear` only destroys active instances, so every room must be woken first with `instance_activate_all()`, and activation takes one event to process. The game does it in `oLink`'s Step (stairs) and builds in the End Step; `oTest` does the same (its Step activates, the next End Step builds). Skipping it leaves enemies of the old level alive, and they crash later with a room index out of range.
* Screenshots: in Post Draw (`Draw_77`) `application_surface` holds the finished frame without the HUD (drawn later, in Draw GUI). The game view is view 1, drawn at 4x at port (288, 0, 1024x896); `Test_CaptureView` copies it back at 1x. Copy with alpha writes off over an opaque surface, or the PNG comes out partly transparent.
* Contact sheet: `Test_SheetStart` hides Link, pauses the game (`global.Paused`) and drives `oCamera` with `Override` (the camera then keeps X/Y as set). Each room is activated in turn and pictured in 256x224 steps. `oLink` must stay active (re-activate him after deactivating a room): `oCamera`'s End Step exits when he does not exist.
* Determinism: `Test_BuildLevel` sets the seed and reshuffles the user's dungeon layout order (`DungeonSeq_Init`, normally done once per new user). A scenario run from the start always plays the same way. But building the same level and seed again later in the same run gives a different level, because the generator keeps state between levels (treasure limiter, prisoners, shop keepers...). So compare levels between runs, not inside one.
* Hooks in the game code: `Test_OnKill` in `Enemy_Destroy`, `Test_Event` in `Achievements_OnBossDefeated`, `Test_OnLevelBuilt` in `Dungeon_InitLevel`. All do nothing outside test mode. More events can be logged the same way.
* The music in a dump depends on the real clock: `oMusic` switches from the intro to the loop when the intro sound ends, so on a busy PC (another test or the validator running) the third build of `ref_01`/`ref_02` can show `SongPlaying_Intro=0`. Not a generator change; run it again alone.
* Level dumps (`"dump": true`): `Test_OnLevelBuilt` runs after every room is built and before `Link_SetStartingPos` puts the rooms to sleep (`with(all)` skips deactivated instances, and activating them again only takes effect in the next event). It writes the level and room structs, every instance with its plain variables and an MD5 of each tile layer per room; `Test_DumpGlobals` (after `Dungeon_InitLevel`) adds the plain global variables. Two runs of the same code give the same file, except the `Time_*` globals (wall clock), which are left out.
* The intro level (`Start`) cannot be rebuilt in the middle of a test: `oIntro` keeps running and crashes on instances of the old level. Its reference scenario only dumps the first build.
* `oCamera.SetToRoomIndex(room, true)` activates the new room and then deactivates the current one, so calling it for the room Link is already in puts Link and the room to sleep (the next frame crashes on `oLink`). `Test_PlaceLink` skips it for the same room.
* Step `trace` logs every enemy each few frames (position, state, sprite, speed, energy, `alarm[0]`): run the same scenario on two versions and compare with `tools/test/logdiff.py` to prove a refactor does not change how enemies move. Step `arch` changes a state of an archetype enemy for one test (e.g. a rat that chases Link). Step `rooms` logs a `layout` line per room of the level (template class, size, template, `set=` when it came from the room set, doors in use as `position:status`, special object, section): build the level in many seeds and count what the room set does not cover (scenario `castle_top_layouts`).
* Scenario `"levels"` changes level sheet fields for that test only (`Test_ChangeLevels`, applied in `Test_Begin`), e.g. a branch no level has yet; step `exit` puts Link in front of the main or extra exit and walks into it; `expect` `"exit_level": true` checks that the level reached is the one that exit led to.
* Debug cheats that work outside tests too: `Test_GotoRoom(gridX, gridY)` (Link just inside one of the room's doors), `Test_SpawnEnemy(objectName, dist)` (in front of Link), `Test_GiveItem(class, index, amount)`.

## Level sheet (`scripts/__Levels`, roadmap F4)

* `global.LevelDefs[DungeonLevel.X]` is one struct per level, made by `Level_Create` (defaults of a normal dungeon level) and filled in `Levels_Init` (called in `INIT` right after `Enemies_InitData`). The macro `LevelDef` is the current level's entry (`global.LevelDefs[global.Level.Index]`). Each field has a comment in the constructor. Several defaults come from the enum index (`Depth`, `Theme`, `BaseTheme`, `EnemyStats`, `Next` = index + 1, `StartDir` by its parity), which only fits the levels in run order: a level added at the end of the enum must set them all. The macro `DungeonLevels` (`__Dungeon.gml`) is a hard 14 that nothing reads.
* `global.Level.Index` is still the key: it is saved with the run, the hub keeps it on Castle, and the stairs go to `Level_NextIndex()` (where the exit taken leads, else `LevelDef.Next`; see "Branched exits"). Only the sheet and the test mode compare it with `DungeonLevel` members.
* Three fields point at another level on purpose: `Theme` (whose art: `LevelTilesY` and every decoration rule written as `switch(LevelDef.Theme)` in `__Dungeon_Draw_*`, `__Decor`, `oCurtain`, `oWallLight`, `oWaterfall`), `BaseTheme` (`LevelTilesY_Base`: door frames, holes, floor trims, stairs; Agahnim borrows the fortress ones) and `EnemyStats` (the level whose stats the enemies with a per-level `Create` take). For today's levels they equal the level itself; a new level that reuses the castle art sets `Theme: DungeonLevel.Castle`.
* `Depth` is how far into the run the level is (1 = Hyrule Castle); difficulty formulas use it (pack points, chances, shop prices, Wallmaster, the HUD progress bar). Old "past the castle" checks are `LevelDef.Depth > Level_Depth(DungeonLevel.Castle)`.
* `Special` (`LevelSpecial`) marks the four levels with fixed layouts and code of their own (intro, village, mines, Agahnim); the rules that only make sense there (grid positions, houses, NPCs) check it.
* Enemies: `Enemies` lists `[object, weight]` (weight = tickets in the draw), `PackPoints` changes an enemy's pack points in that level (`{oEnemy_Rat: 1}`). `Level_EnemyWeight(object)` reads it; the room generator still walks the objects in index order, so the random draws are the same as with the old table.
* The constructor's field names must not match an enum, macro, function or asset name: `SecretDoor = SecretDoor.Crack` inside `with(struct)` is ambiguous, so the field is `SecretDoorType`.

## Branched exits (roadmap F4b)

* A level's exit is not a room: it is a door with `DoorStatus.Exit` in the top or bottom wall of a room, drawn as a stairway in the doorway; Link walking into it goes `Descending` (`CheckDoors` in `__Link`). Every layout in `data_d` has one exit room with three Exit doors (top, left, right before the transform); `Dungeon_InitLevel` keeps the one on the side `StartDir` asks for and marks the others `Unused`. That room is `RoomIndex_BossAdjacent` in every level; in boss levels its top door leads to the boss room instead, and the boss room's top door becomes the exit when the crystal is picked up. The room template class Stairs is unrelated: rooms with inner stairs between the upper and lower floor.
* Pools in the level sheet: `NextPool` (where exits lead, default `[[Next, 1]]`), `ExitCount`, `ExitHidden`, `ExitMinDistance`; `Level_PoolPick` draws from `[value, weight]` pairs and uses no random number for a single entry. `Dungeon_PlanExits` (right after the room structs, before the secret rooms and the templates) does nothing more unless `Level_Branches` (the pool has two different levels): so today's levels draw nothing and are built as before F4b (the 14 reference scenarios compare SAME).
* The extra exit is added to `Room.Doors` only (never to the layout's `DungeonRoom.Doors`), always as the last door, with `ExitDest` set; code that walks `Room.Doors` must not index `DungeonRoom.Doors` with the same index (the carpet code did; fixed). Where it goes: a 1-wide room with only upper-floor doors and no section, door position 12 (top middle) or 6 (bottom middle) with no room behind that wall, at least `ExitMinDistance` columns from the main exit room and on the other side of the map's middle column. Hidden: a special room with one door, made secret (`Dungeon_HideSpecialRoom`) and never with an Illusion wall (that one is walked through, not bombed). No candidate: hidden falls back to visible, then to one exit. If no room template has a door there, `Dungeon_DropExtraExit` takes it out and the template is picked again. Not in boss levels (it would skip the boss) nor in fixed layouts (`Special`).
* `global.Level.Exits` = `{Dest, ExtraRoom, ExtraPosition, ExtraSecret}`. `Door_ExitDest(oDoor)` is the level a door leads to (the door struct's `ExitDest`, else `Exits.Dest`; in the rest stop, `Level_NextIndex()`). Taking an exit stores it in `global.RunPath.Next`, which the End Step of `oLink` reads through `Level_NextIndex()` (falls back to `LevelDef.Next`); it lives through the rest stop and goes into the save (`SaveData.NextLevel`). `Dungeon_InitLevel` resets it. The intro still uses `LevelDef.Next` to enter the castle.
* Looks: `global.ExitLooks` (`ExitLooks_Init`, `__Doors`), named by the destination level's `ExitLook`. `Door_DrawTiles` draws the door sides and calls `Door_ExitLook(inst).Draw` for the beam and the doorway; the sound when Link goes through it, Link's animation and the sound when he arrives at the next level, and the large map icon also come from the look. `oLink.ExitLook` keeps the look of the exit Link took (set by `CheckDoors` before `UpdateState(LinkState.Descending)`, the state for every look) until the arrival: `ExitLook_LinkSprite(look, phase, TOP|BOTTOM)` gives `global.LinkSpr_<LinkAnim>_Top1/_Bottom1` (leaving, `UpdateSprites`) and `_Top2/_Bottom2` (arriving, `oLink` End Step), and Alarm 9 plays `ArriveSound`. The phase ends when the sprite's last frame plays, so a look's sprites set its timing; the last frames of the leaving ones stay blank because that frame stays on screen while the level loads. `Ascending` (StairsUp) is made from the `Descending` sprites by `LinkSprite_Remix` (each frame picked, moved and mirrored, cut at the sprite's edges, which are the doorway's sides), following the steps drawn in the doorway: the arrival doorway is the look's `Entrance` (`[top, bottom]` decor tile column, drawn by `oLink`'s End Step), and `StairsUp` lands on the stairway going down, as ALttP does after going up. Each Ascending sprite is a mirrored Descending one taking the same steps the other way. The path is that of ALttP's spiral stairs up (zelda3 `HandleLinkOnSpiralStairs`: down goes left at the same height, up goes right and up; `SpiralStairs_FindLandingSpot`: down lands moving left and down, up lands moving right, level).
* Link's sprite offsets: `Stand_Down` draws the body 13 px above `y` and the head 21 px above (origin 8,21); `Walk_Down` frame 0, 11 and 19. An animation that hands over to standing or walking must end at those heights or Link jumps. `Descending_Top2` is 24 px tall (origin 8,23): its sideways frames clear the 8 rows above the doorway (`LinkSprite_ClearRows`), the last two step down to the standing height.
* The rest stop builds with `LevelDef` = the level before it (`Dungeon_InitSaveLevel(global.Level.Index)`), so that level's flags (`RunStart`...) apply in it.
* Trap: `UpdateState` calls `UpdateSprites` BEFORE its `switch` on the new state, so a variable that the sprite choice reads must be set before `UpdateState`, not in its `case`. `StairsDown` is the old exit (beam 58, doorway 60 on top / 58 at the bottom); `StairsUp` is what the entrance of every level shows (ordinary beam 50, doorway 58 on top / 60 at the bottom, drawn by `oLink`'s End Step on arrival).
* To keep the reference dumps comparable, the new state lives in structs (`global.Level.Exits`, `global.RunPath`, `global.ExitLooks`) and in the door structs, not in plain globals or `oDoor` variables: the dumps skip structs.

## Enemies (`scripts/__Enemies`)

* `Enemies_InitData` registers every enemy with `EnemyDataInit(object, energy index, attack, special item, item, pack points, [weapon effects])`. Which levels it appears in, and how often, is in the level sheet (`Enemies`). An enemy object with no entry is never placed by the room generator (several exist: Delavant, Kyune, Lynel, Pirugusu, Soldier_Slasher).
* Energy index means hits to kill, through `global.EnemyHitsToKill[attack points][index]`. Attack points are `ATTACK()` = sword index + 1 + glove index (minus the curse). Damage to Link is `Attack` in hearts minus 0.25 per defense point, at least 1/8 (`Enemy_Attack`).
* Many enemies override the table's energy and attack by level: soldiers through their variant (below), Poe, Wizzrobe, Beamos in their `Create` (`switch(LevelDef.EnemyStats)`), and Bari, Bubble, Gibdo, Keese, Kodongo, Octorok, Ropa, SnapDragon (`Type` from a comparison with `LevelDef.EnemyStats`), Wallmaster (formula on `LevelDef.Depth`), Guru bars (`LevelDef.GuruBarType`). Fortress soldiers set theirs in `Step_1` from the random head. `docs/ref/doi.md` lists them all; check the object before trusting the table.
* Per-level variants (`scripts/__EnemyArch`, roadmap F7): `EnemyVariant(object, default, [[level, {...}], ...])` in `EnemyVariants_Init` holds what an enemy changes per level as instance variables (`ColorIndex`, `HeadIndex`, `Weapon`, `Size`, `Attack`; `Energy` is the energy index; a list is a `choose`). `Enemy_ApplyVariant()` takes the level sheet's own (`LevelDef.EnemyVariants`, `{oEnemy_X: {...}}`), else the one of the level `EnemyStats` points at, else the default, and sets the fields in name order. The soldiers (`oEnemy_Soldier_Simple`, `_Advanced`, `_Mace`) call it in place of their old `switch`; their default is their first level's, so they work in any level (before F7 they crashed with `Weapon not set`).
* Archetype enemies (`scripts/__EnemyArch`, roadmap F7): an object whose parent is `oEnemy_Archetype` and that has no events is driven by its `EnemyArch(object, {...})` entry: `Vars`, `Start`, `States` (`Time`, `Next`, `Move`: `Dir`, `Toward`, `Scuttle`, `Dash`), `Recover`, `Sprites` (a base name; `_Left/_Right/_Up/_Down` found by themselves), `Palette` (indexed by `ColorIndex`), `Shadow`, `Flip`, `InWaterW`, `StayOnWater` and the flags `Trap`, `Flies`, `Jumps`, `Hides` (read by `Enemy_GoodForTrap`, `Enemy_CanFly`, `Enemy_CanJump`, `Enemy_CanBeHidden`). The field list is at the top of the script. Converted so far: rat, rope, crab, hover (same behaviour frame by frame, `tools/test/scenarios/arch_trace.json`).
* How the archetype is hooked in: `Enemy_UpdateState` calls `EnemyArch_UpdateState()` right after `State = NewState` and, for a state the entry lists, only adds `Enemy_UpdateSprite`; `Enemy_UpdateSprite` calls `EnemyArch_UpdateSprite()` first. States the entry does not list (knockback, stun, fire, death...) run oEnemy's code as before. The entry is found with `EnemyArch_Get(object_index)`, so a converted enemy keeps exactly the instance variables it had (no new ones), and the dumps of the reference scenarios do not change.
* Trap: code that asks "is this an enemy?" with `object_get_parent(object_index) == oEnemy` misses the archetype enemies (their parent is `oEnemy_Archetype`). `WallCollision` (`__Collision`) had it, and the converted rope walked through walls until it treated `oEnemy_Archetype` as `oEnemy`. Use `object_is_ancestor` or check both in new code; `with(oEnemy)` and collisions with `oEnemy` already include them.
* Writing Python through a shell heredoc: an escape like `\b` inside a normal (not raw) Python string becomes a backspace character, invisible in `git diff`. The validator's `ExitLook` check carried one from F4b to F7 and never matched anything. In F3b the same happened to `\0` in `run.py` (a NUL byte: `file` calls the script "data" and `grep` says "binary file matches"), and `\n` in a `python -c` replacement turned into a real line break. Write such scripts and edits with the Write and Edit tools, and check with `python -c "print(open(f, 'rb').read().count(b'\x00'))"` or `file <script>`.
* Same random draws: the archetype code calls `choose` with the same number of arguments as the old code (`EnemyArch_Choose` spreads a list into `choose(a, b, c)`; a list of one draws nothing) and in the same order, so a converted enemy makes the same moves with the same seed.
* Numbers for every enemy are collected in `docs/ref/doi.md`.

## Tile bands and region tilesets (roadmap F6b)

* **A tileset draws from `tilesets/<name>/output_tileset.png`, not from its sprite.** The IDE writes that texture when a tileset or its sprite changes; Igor only copies it. A tileset without it builds fine and draws nothing (`tileset_get_info` gives `texture: -1`, `width: 0`), and a taller `sTiles` without a new texture would draw nothing from the new rows. Format, checked against the IDE's file for `sTiles` (identical pixels): each tile in a 12x12 cell, its edge pixels repeated 2 px around it (`out_tilehborder`/`out_tilevborder`), `out_columns` cells per row, the rounded up square root of the tile count (125 for 15600), rows as needed; cell 0 holds the IDE's empty tile mark. `import_region.py` (`tileset_texture`) writes it with `out_columns` and `tile_count`, and the validator checks that every tileset has one of the right size.
* **Tile bands:** a region's band (`incoming/<region>/tileset.png`, laid out like a theme band) is pasted into `sTiles` at rows 100, 106, 112... and named in `TileBands_Init` (`__Tiles.gml`, one line per band, written by the importer). `TilesBand` in the level sheet picks it: `LevelTilesY` reads `global.TileBands[$ TilesBand]` instead of the Theme's rows. `Theme` still decides the decoration rules (`switch(LevelDef.Theme)`) and `BaseTheme` the door frames, holes, trims and stairs (`LevelTilesY_Base`), so a band must keep the layout of the theme it says it follows. Tile ids only grow at the end (`row * 156 + column`), so the original tiles keep their ids. Proof (out/2026): Hyrule Castle with a copy of the Castle band tinted blue at rows 100-105 builds the same three levels as `ref_01_Castle`; the dumps differ only in the tile ids (96 rows later: `CarpetTileBase` 1047 becomes 16023), with the same tiles used per layer. Removing the band brings `sTiles` and the texture back to the same pixels (the PNG bytes change, so restore them with git if nothing else changed).
* **Region tilesets:** `ts_<Name>` over the sprite `sTileset_<Name>`, plus `datafiles/data/tiles/<Name>.json` (included file): `class` (one per tile, tile 0 empty), `blocks` (16x16 painting units, four `[tile, flags]`, flags 1 mirrored, 2 flipped) and `animated`. `RegionTiles` in the level sheet names it; `RegionTiles_Get` loads the file on first use (cached in `global.RegionTiles`, `Region tileset loaded: ...` in the output), `RegionTiles_PaintBlock(block, x, y, floor, mirror, flip)` paints, `RegionTiles_ClassAt(x, y)` reads the class back. The tiles go on two layers made at runtime the first time something is painted, `Tiles_Region_Upper` (depth 1350, between the upper water 1300 and floor 1400) and `Tiles_Region_Lower` (2150); `Dungeon_Clear` empties them, and a level with another tileset switches the tilemap's tileset. They have no layer script, so the lighting shader (`PixelRender`) does not darken them yet; an outdoor level is never dark, but painting inside a dark dungeon would need a `layer_script_begin` like the other tile layers.
* **The asset name `Tileset` is a constant in GML:** a struct field called `Tileset` does not compile ("Cannot set a constant"), which is why the level sheet field is `RegionTiles`. Any field named like an asset (sprite, sound, tileset, object) has the same problem.
* The test dumps skip struct globals (`Test_ValueStr` gives undefined for structs), so `global.TileBands` and `global.RegionTiles` do not change the reference dumps; a new plain global would add a line to every dump.
* Python trap in the tools: `open(p, 'w').write(open(p).read().replace(...))` empties the file, because `open(p, 'w')` runs (and truncates) before the read. It wiped `__Tiles.gml` once during F6b; read into a variable first.
* Tile bands and region tilesets come from the importer; `tools/alttp/owdump.py tiles` cuts ALttP overworld areas into a region tileset (the classes come from the ROM's tile attributes; tiles kept once, flips reused, old indices kept when areas are added).
* **Import hashes and line endings:** `core.autocrlf=true` checks text files out with CRLF on Windows, so a raw sha1 of `manifest.json` or `tiles/tiles.json` differs from the one recorded on a checkout with LF and the validator reported "changed since the last import" with nothing changed (out/2026). `import_region.source_hash` hashes text sources (`.json .txt .csv .tmx .tsx .ini`) with LF; binary files as they are.
* **Composing a band:** `tools/import/compose_band.py <region>` builds `incoming/<region>/tileset.png` from a theme band and the region blocks by a recipe (`band.json`: recolor by luminance rank, blocks, 8x8 quarters, fills, crenels). Band layout of the Castle theme as the walls read it (`__Dungeon_Draw_Walls`): upper walls columns 0-16, lower 17-33 (same layout + 17); outer corner 3x3 at 0,0, drawn rotated for the other three (`DrawTileBlockRotate`), so a band cannot light the corners differently; side T at 6-7 rows 0-2 and side B at 9-10 rows 2-4 (column picked by `TileX mod 16`), side L at 6-8 row 3 or 4 and side R at 8-10 row 0 or 1 (by `TileY mod 16`); inner corners 3x3 at 11 and 14, rows 0 and 3; ceiling (outside the rooms) tile 8,2; floors 2x2 at 42 (main upper), 44 (main lower), 46 and 48 (alternates); floor trim from 44 rows 2-5; carpet base 111,2 and trim 110,4.

## Painted rooms (roadmap F12b-1)

* A room template can be painted tile by tile with the level's region tileset instead of the generated walls. In Tiled it is a `Main_Upper` room with the property `Whole` 1 (a whole room, 1x1 or 1x2, never joined with a half: the bottom half is flipped upside down, which breaks ALttP art) and two tile layers over the region's Tiled tileset (`data/room-templates/tilesets/<Region>.json`, written by the importer over `incoming/<region>/tiles/tiles.png`; tile i is tile i of `ts_<Region>`): `Region`, the room with every door closed, and `RegionOpen`, the passage of each door. `convert.py` writes `Region: {tileset, w, h, base, open}` (8x8 tiles row by row, `index | flags << 16`, flags as Tiled applies them: 1 mirror, 2 flip, 4 diagonal, diagonal first; 0 no tile) and `RoomTransformationsAllowed` from the property `Transforms` (default `None,FlipH`).
* `RoomTemplates_PickFrom` keeps the transform it picked in `Template.Transform` (only for painted templates). `RegionRoom_Paint` (in `Dungeon_InitLevel`, right after `Dungeon_Draw_Walls`) moves each tile like `TransformObjArray` moves objects (`RegionTiles_TransformCell`) and turns its flags (`RegionTiles_TransformFlags`, 2x2 matrices), paints the base on `Tiles_Region_Upper`, then for every door in use paints the `open` tiles 4-connected to the door's 32x32 cell (`RegionRoom_OpenPassage`; a secret door does it when bombed, from `Door_OpenSecretDoor`), and makes the walls (`RegionRoom_Walls`: runs of solid tiles per row, equal runs merged down, each an `oWall` with `RegionRoom` set, made again when a passage opens). The walls are kept by id in `RegionGrid.Walls`: a bombed secret door opens the passage of the room behind it too, and that room sleeps (`instance_deactivate_region`), where `with(oWall)` does not reach; the old walls are woken by id, destroyed, and the new ones put back to sleep (found in review, out/2026: the room behind kept its old walls, doubled, and the passage stayed shut). `Room.RegionGrid` (`W`, `H`, `Tiles`, `Open`) exists only in painted rooms; `RegionRoom_Is` tests it. Painted rooms get no ceiling, and `Dungeon_CreateDoors` does not cut their walls at the doors (the passage is already open).
* Which tiles are walls: `solid` in `data/tiles/<Region>.json`, written by the importer from the tile classes (`TILE_WALKABLE` in `import_region.py`: floor, shallow water, tall grass, stairs, entrance, dig, warp; every other class, ledges, bushes, rocks, pits and deep water included, is a wall until it has its own object).
* **GameMaker turns a tile 90 degrees clockwise before it mirrors and flips.** Clockwise is the diagonal (transpose) followed by a mirror, so a tile with Tiled's diagonal flag gets `tile_set_rotate` and the mirror bit the other way round (`RegionTiles_TileData`). Checked in the shot `transforms` of the scenario `castle_top_room`: the eight transforms of an asymmetric corner piece come out whole.
* `LevelDef.Layout` (`LevelLayout.Dungeon` or `Outdoor`): in an outdoor level an open door (status `Open` or `Curtain`) of a painted room draws no frame (a room of the shared templates keeps its frames, its walls being the dungeon's) (`Door_DrawTiles` clears the door cell and stops); the passage is the painted one. Locked, closed, secret, entrance and exit doors still draw the dungeon doors (the castle theme's frame and door in the cut of the parapet, the beam of a side door showing above the cut): readable, waiting for Guilherme's verdict on an outdoor look.
* Painted rooms are never turned (their light would be wrong), so each size has its own: `1x1`, `1x2` and `2x1` (a 512x256 room, `SizeIndex` 2, kept with the 1x2 templates, since 2x1 rooms look there). `RoomTemplates_PickFrom` takes a painted template only for a room of its own `SizeIndex` and skips the rotations-only rule of 2x1 rooms for it.
* Which doors a painted room has decides which rooms it fits (the template's doors must include the room's). The passages of neighbouring positions touch (the opening is wider than the 32 px door cell), and the 12 positions of a 1x1 room make a ring where each touches the next (11, 12, 1 on top, 1 with 2 at the corner...): a 1x1 room takes no two neighbours. The Castle layouts never put two neighbours in a room either (12 seeds), so a few independent door sets cover every room: six for the rooftops' 1x1 rooms. In 1x2 rooms the side positions are far apart, in 2x1 rooms the top and bottom ones. Rooms with a section (`Section_ID`, part of the room cut off in the layout) need a template with that section in `Split_MainSectionIDs`, which painted rooms never have: they take a shared template.
* `ObstacleRooms` in the level sheet (default true): false makes the rooms that would draw an obstacle template (`Chance_ObstacleTemplate`) take a `Main_Upper` one; the rooftops have no obstacle rooms, which are dungeon puzzles. The flag is read before the `Prob`, so every other level draws the same numbers.
* The level's `RegionTiles` must be the tileset the room is painted with (`RegionRoom_Paint` stops with an error otherwise; the validator checks every level whose `RoomSet` has painted rooms).
* A new room set, a new level sheet field (`Layout`) and the painted room code change none of the 14 reference levels: `baseline.py compare --handles` gave every scenario the same as before F12b-1 (the test logs do not carry the `Room sets loaded` line, and the dumps skip struct globals such as the level sheet).

## IDE messages (Feather)

* The IDE's Feather panel ("Mensagens de Pena") shows analysis messages the Igor build ignores: a build can pass every scenario and the IDE still list "errors". Read them when the project opens. Two kinds seen (out/2026, F12b-1): `GM1020` (a call with fewer arguments than the function has; `Error` now defaults `_GameEnd` to false, since `if(undefined)` can stop the game right when it reports an error) and `GM2044` (the same `var` declared twice in one function, e.g. in two `case`s of one `switch`; the code has about 300 of them from before, mostly loop counters, so the validator does not check it: use a different name in new code).

## Sound effects (roadmap F6b)

* Effects are in `audiogroup_SFX` (music in `audiogroup_Music`), mono 22050 Hz like `Sound_Rain`. The importer makes `incoming/<region>/sounds/<Name>.wav` into `Sound_<Name>` in that group (`gm_assets.sound(..., group, channels, volume)`).
* From the ROM: ALttP plays an effect by writing its number to an APU port for one frame (`src/nmi.c`): port 1 the ambient sounds (`sound_effect_ambient`, the rain is 1), 2 `sound_effect_1`, 3 `sound_effect_2`. The thunder of the rain is 54 (0x36) on port 2 (`OverworldOverlay_HandleRain`). `musicdump.c sfx <port> <number> <seconds> <out.pcm>` renders it through zelda3's SPC emulation; `tools/alttp/sfx.py` builds, renders, cuts the silence and writes the `.wav` (the thunder: 1.69 s).
* Building the C harnesses without Visual Studio: `tools/alttp/build.py` compiles with gcc, clang or the clang inside the `ziglang` Python package (`python -m pip install --user ziglang`), leaving out zelda3's `src/main.c`, `config.c`, `opengl.c` and `glsl_shader.c` and standing in for SDL's key header, the config globals and opus with `tools/alttp/stub/`. The harnesses read `zelda3_assets.dat` from the zelda3 folder, made by zelda3's own `python assets/restool.py --extract-from-rom` (needs PyYAML).
* Colors: the original DoI sprites use web safe steps of 51 (`51,51,51` outline, `153,51,0`), the ROM extractions of the hub use the SNES levels written as `round(n*255/31)` (`33,49,41`). The importer writes the second form. Palette swap sprites (`*_Pal`, e.g. `sEnemy_Rat_Pal`) are matched color by color by the palette shader, so a sprite and its `_Pal` must be converted the same way.
* Sprite origin in the `.yy`: `origin` 0 top left, 4 middle center, 7 bottom center (`yorigin` = height), 9 custom. Speed is `playbackSpeed` in frames per second (`playbackSpeedType` 0).
* Igor builds only what changed: the `boot` scenario with six new sprites and two sounds compiled in about 20 s. To confirm the new assets are in a build, look for their names in `%TEMP%\doi-test\output\Zelda\Zelda.win`.

## Assets from A Link to the Past

Room pictures, sprites and music were taken from the original game with small harnesses built on the zelda3 reimplementation (room render with animated tiles, sprite OAM dump, SPC music render). Music is split into an intro and a loop (`Music_Sanctuary_Intro`, `Music_Sanctuary_Main`).
